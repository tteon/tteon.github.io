## 1. Motivation: One Default Runtime Cannot Serve Every Agent Query Shape

Graph-based LLM agents emit two completely different kinds of Cypher in the same session: sub-millisecond entity lookups (`W1`) alongside unanchored multi-hop neighborhood scans (`W4`). Before writing query-shape routing heuristics into our Rust Bolt middleware, we needed direct proof on managed Neo4j Aura of where `slotted`, `pipelined`, and `parallel` actually change client wall time—and where TLS network round trips drown out executor choices.

## 2. Worked Query Shapes & Experimental Setup

Six canonical graph workloads (`W1`–`W6`, 5 measured runs each = 90 runs) were run under explicit `CYPHER runtime=slotted`, `pipelined`, and `parallel` hints. Consider the two opposite extremes from `workloads.py`:

```cypher
// W1_point_lookup — single indexed seed (~1–2 ms server work)
MATCH (n:AuraRuntimeLabNode {id: 101})
RETURN n.id AS id, n.segment AS segment, n.score AS score

// W4_global_3hop_analytics — full 3-hop scan across filtered endpoints (~6.1M–10.0M DB hits)
MATCH (a:AuraRuntimeLabNode)-[:AURA_LAB_LINK]->(b)-[:AURA_LAB_LINK]->(c)-[:AURA_LAB_LINK]->(d)
WHERE d.score >= 30
RETURN a.segment AS segment, count(*) AS path_count, avg(toFloat(d.score)) AS mean_score
ORDER BY path_count DESC, segment ASC LIMIT 20
```

Every run verified identical SHA-16 result digests across all three runtimes (`PASS (1 result digest)` for all 6 workloads).

## 5. Mechanism Breakdown & Decision Rule

Inspecting `measurements.csv` explains both sides of the curve cleanly:

- **Why shallow queries stay flat (`W1`, `W2`, `W5`)**: On `W1`, server first-result + consume time is only 1–2 ms (`4` DB hits), whereas the TLS client wall time is 100–106 ms. Requesting `parallel` on `W1` allocates `2.23 MB` of worker memory vs `64 B` on `slotted` purely to sit behind network RTT. Even on `W2` (local 3-hop from one seed node, `1,755`–`2,850` DB hits), server time is 2–6 ms, so `parallel` (`2.75 MB`) yields `0.97×` slowdown.
- **Why global traversals diverge (`W4`)**: Scanning across unanchored `3-hop` neighborhoods executes `6.14M` DB hits in `slotted` (`2,099`–`2,300 ms` server consume) vs worker-partitioned `PartitionedNodeIndexSeekByRange` in `parallel` (`270`–`602 ms` server consume), explaining the `4.11×` speedup.

<Callout type="decision" title="Practical Query-Routing Heuristic">
Route by expected operator work relative to your Bolt network RTT: (1) use **Slotted/Pipelined** for single-node lookups, indexed top-k, and bounded seeded traversals (`W1`, `W2`, `W5`); (2) trigger **Parallel** only when `EXPLAIN` shows global label/index-range scans feeding multi-hop `Expand(All)` aggregations (`W3`, `W4`, `W6`).
</Callout>

## 6. Scope Limits & Next Experiment

- **Single-stream measurement**: Runs were executed sequentially (`n=5`). Because `parallel` claims multiple worker threads and 2–6 MB heap per query, high-concurrency throughput can favor `pipelined` or queue admission control.
- **PROFILE instrumentation overhead**: Client wall timings include `PROFILE` operator collection overhead.
- **Next step**: Measure concurrent agent throughput (concurrency 8–64) and Rust Bolt admission-queue latency when mixed `W1` + `W4` workloads collide.
