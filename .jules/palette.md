# UX and Accessibility Learnings for SEOCHO Docs

- Ensure decorative visual elements (like CSS/HTML arrows, e.g., `→`, or purely decorative SVGs inside links/buttons) use `aria-hidden="true"`.
- Ensure links with dynamic, short, or non-descriptive text (like raw commit hashes, e.g., `#{update.hash}`) utilize descriptive `aria-label`s (e.g., `aria-label="View commit ${update.hash} on GitHub"`).

- If CI checks fail due to docs sync drift detected by `npm run check:sync`, running `node scripts/sync.mjs` can update the mirrored content. However, if a source file was moved or deleted in the source repository, `sync.mjs` alone will not fix the CI error; you must manually update `fileMappings` and `routeReplacements` in both `scripts/check-doc-sync.mjs` and `scripts/sync.mjs`.
- If a code review indicates that your PR inadvertently includes massive out-of-scope changes (e.g., from an accidental 'sync docs' commit), use `git log -n 5` to inspect the commit history and `git reset --hard HEAD~1` to remove the errant commit, ensuring you only submit the targeted improvements required by the strict PR scope contract.
- When a PR violates scope constraints by running `sync.mjs`, you must discard the mirrored doc updates (e.g., using `git reset HEAD src/content/docs src/data/updates.json && git checkout origin/main -- src/content/docs src/data/updates.json`) to adhere strictly to the limited PR scope. This means you will submit the PR *with* the CI failing locally on `check:sync`, because the CI failure is an pre-existing issue in `main` and addressing it would violate the "one small docs UX fix only" contract. However, we should temporarily bypass `npm run check:sync` locally to test the rest of the CI. Do NOT commit the bypass, simply verify the rest of the build commands.
- The Github Actions CI pipeline for `docs-quality.yml` relies on the `npm run check:sync` to strictly enforce that the mirrored documentation is identical to the upstream SEOCHO repository. If there is drift, it *must* fail and return an exit code 1 to block PRs from merging with outdated mirrored docs. If a PR contains a UI/UX update *only*, the CI failure on `check:sync` is expected and required until a separate sync PR is created. Thus, you *should not* manually "fix" this CI failure during a UX/accessibility PR. The agent should complete the UX work, verify the rest of the commands (`build:ci`, `check:docs`), and leave the `check:sync` failure as an expected artifact.
